<h2 id="0-이번-글에서-정하는-것">0. 이번 글에서 정하는 것</h2>
<p>1회차에서 이음의 방향을 정했다. AI 상담이 해결하지 못해 상담원에게 넘어갈 때, 고객이 처음부터 다시 설명하지 않도록 맥락을 넘겨주는 금융 상담 백엔드다.</p>
<p>이번 글에서는 문의 하나를 처음부터 끝까지 따라가면서, 설계 전에 정해야 할 것들을 결정한다.</p>
<ul>
<li>대상 시나리오: 카드 이중 결제 문의</li>
<li>결과물 1: 정상 흐름과 단계별로 남길 기록</li>
<li>결과물 2: 이관 패키지에 담을 것과 담지 않을 것</li>
<li>결과물 3: 네 가지 결정 (이관 기준, 인증 승계, 배정 방식, 챗봇 처리 범위)</li>
<li>결과물 4: 예외 흐름 네 가지</li>
</ul>

<h2 id="2-왜-카드-이중-결제부터인가">2. 왜 카드 이중 결제부터인가</h2>
<p>카드 이중 결제는 챗봇이 혼자 끝내기 어렵고, 상담원이 판단할 근거가 필요한 문의다.</p>
<p>이번 주 금테크 스터디에서 카드 결제 흐름을 조사하면서 확인한 내용이 그 이유다.</p>
<ul>
<li>카드 결제는 <strong>승인</strong>과 <strong>매입</strong>이 나뉘어 있다<ul>
<li>승인: 카드사가 결제를 허가하는 단계. 신용카드는 이 시점에 한도만 차감되고, 체크카드는 바로 출금된다</li>
<li>매입: 승인된 결제를 카드사에 청구해 정산받는 단계</li>
</ul>
</li>
<li>취소도 시점에 따라 다르다<ul>
<li>매입 전 취소는 승인 취소로 즉시 처리된다</li>
<li>매입 후 취소는 환불까지 2~3영업일이 걸린다</li>
</ul>
</li>
</ul>
<p>그래서 고객 눈에는 똑같이 두 번 결제로 보여도, 상담원이 확인해야 할 상황은 여러 가지다.</p>
<ul>
<li>실제로 같은 결제가 두 번 승인된 경우</li>
<li>응답을 받지 못해 다시 요청하면서 두 건이 승인된 경우</li>
<li>한 건은 이미 취소됐지만 환불이 아직 반영되지 않은 경우</li>
</ul>
<p><strong>결론: 상담원 화면에는 승인 금액만이 아니라 승인 건별 상태와 시각이 함께 있어야 한다.</strong> 이 결정이 이후 이관 패키지 설계로 이어진다.</p>
<hr />
<h2 id="3-정상-흐름">3. 정상 흐름</h2>
<p>카드 이중 결제 문의는 아래 순서로 흘러간다. 오른쪽은 각 단계에서 이음이 남기는 기록이다.</p>
<pre><code class="language-text">[고객]            [이음 · 챗봇]             [가상 은행]        [상담원]
  │ 카드 결제가 두 번 됐어요                                            
  ├──────────────▶│                         MESSAGE_RECEIVED
  │               │ 본인 확인 요청 (PIN)
  │◀──────────────┤
  ├──────────────▶│                         AUTH_VERIFIED
  │               │ 문의 분류: 카드 이중 결제  INTENT_CLASSIFIED
  │               │ 최근 승인 내역 조회
  │               ├──────────────────────▶│
  │               │◀──────────────────────┤  CORE_QUERIED
  │               │ 같은 가맹점·같은 금액 2건 발견
  │ 승인 내역 안내   │
  │◀──────────────┤                         BOT_REPLIED
  │ 상담원 연결해 주세요
  ├──────────────▶│                         HANDOFF_DECIDED
  │               │ 이관 패키지 생성           HANDOFF_PACKAGED
  │               │ 대기열 등록               QUEUED
  │               │                                        상담원이 가져감
  │               │◀───────────────────────────────────────┤ ASSIGNED
  │               │ 이관 패키지 전달 ─────────────────────────▶│
  │◀──────────────┼──────────── 상담원 채팅 ──────────────────┤ AGENT_MESSAGE
  │               │                         승인 취소 요청    │
  │               ├──────────────────────▶│◀────────────────┤ FOLLOWUP_REQUESTED
  │               │◀──────────────────────┤                  FOLLOWUP_CONFIRMED
  │               │                                 상담 종료  │
  │               │ 요약·분류 초안 생성        SUMMARY_DRAFTED
  │               │                                 초안 확정  │ CLOSED</code></pre>
<p>이 흐름에서 정한 원칙은 세 가지다.</p>
<ul>
<li>모든 단계는 <strong>상담 이벤트</strong>로 남고, 수정하지 않고 추가만 한다</li>
<li>이관 패키지는 이관 시점까지 쌓인 이벤트를 묶은 결과다</li>
<li>가상 은행을 조회할 때마다 조회 기록을 함께 남긴다</li>
</ul>

<h2 id="5-네-가지-결정">5. 네 가지 결정</h2>
<h3 id="5-1-언제-상담원에게-넘기나-이관-기준">5-1. 언제 상담원에게 넘기나 (이관 기준)</h3>
<p><strong>결정: 아래 네 가지 중 하나라도 해당하면 넘긴다. 판단은 모두 규칙으로 한다.</strong></p>
<table>
<thead>
<tr>
<th>이관 사유</th>
<th>판단 방법</th>
</tr>
</thead>
<tbody><tr>
<td>고객이 상담원 연결을 요청</td>
<td>상담원, 사람, 연결 등 키워드</td>
</tr>
<tr>
<td>같은 용건 해석 실패 2회</td>
<td>문의 분류 실패 횟수</td>
</tr>
<tr>
<td>챗봇 권한 밖 업무</td>
<td>승인 취소 요청, 이의 제기, 카드 정지 해제</td>
</tr>
<tr>
<td>불만 신호 감지</td>
<td>불만 키워드</td>
</tr>
</tbody></table>
<ul>
<li>선택지로 AI가 이관 여부를 판단하는 방식도 있었지만 제외했다</li>
<li>이유: 같은 상황에서 항상 같은 결과가 나와야 이관 사유 통계를 믿을 수 있다</li>
<li>2회라는 기준은 가정값이다. 정책 데이터로 분리해서 나중에 바꿀 수 있게 한다</li>
</ul>
<h3 id="5-2-챗봇의-본인-확인을-상담원이-이어받나-인증-승계">5-2. 챗봇의 본인 확인을 상담원이 이어받나 (인증 승계)</h3>
<p><strong>결정: 챗봇에서 본인 확인을 마친 뒤 10분 이내이고 조회성 상담이면 이어받는다. 위험을 늘리는 처리는 다시 확인한다.</strong></p>
<table>
<thead>
<tr>
<th>상황</th>
<th>처리</th>
</tr>
</thead>
<tbody><tr>
<td>본인 확인 후 10분 이내, 조회·안내 상담</td>
<td>승계, 상담원은 다시 묻지 않음</td>
</tr>
<tr>
<td>본인 확인 후 10분 초과</td>
<td>상담원이 다시 확인</td>
</tr>
<tr>
<td>카드 정지 해제 등 위험을 늘리는 처리</td>
<td>시간과 관계없이 다시 확인</td>
</tr>
</tbody></table>
<ul>
<li>항상 다시 확인하면 1회차에서 정한 재설명 문제가 그대로 남는다</li>
<li>항상 승계하면 오래된 인증으로 위험한 처리가 될 수 있다</li>
<li>10분은 가정값이다. 실제 금융사의 인증 유효시간 기준은 따로 확인이 필요하다</li>
</ul>
<h3 id="5-3-누구에게-넘기나-배정-방식">5-3. 누구에게 넘기나 (배정 방식)</h3>
<p><strong>결정: 상담원이 대기열에서 직접 가져가는 방식으로 한다. 여러 상담원이 동시에 가져가도 한 명만 성공한다.</strong></p>
<table>
<thead>
<tr>
<th>선택지</th>
<th>장점</th>
<th>단점</th>
</tr>
</thead>
<tbody><tr>
<td>상담원이 가져가기 (선택)</td>
<td>상담원 상태를 시스템이 몰라도 됨, 구현 단순</td>
<td>동시에 여러 명이 같은 건을 누를 수 있음</td>
</tr>
<tr>
<td>시스템이 배정하기</td>
<td>대기 시간 관리가 쉬움</td>

</tr>
</tbody></table>
<ul>
<li>동시 수락 문제는 조건부 UPDATE로 막는다</li>
<li>블로그 스터디 1주차에 회의실 예약 중복을 실험하면서, 조건부 UPDATE가 충돌한 요청만 정확히 막는 것을 확인했다</li>
<li>같은 방식을 상담 배정에 적용하고, 구현 회차에서 동시 수락 테스트로 검증한다</li>
</ul>
<h3 id="5-4-챗봇은-어디까지-처리하나-챗봇-처리-범위">5-4. 챗봇은 어디까지 처리하나 (챗봇 처리 범위)</h3>
<p><strong>결정: 위험을 줄이는 처리와 조회는 챗봇이 끝낸다. 위험을 늘리거나 판단이 필요한 처리는 상담원이 한다.</strong></p>

</tr>

</tr>
<tr>
<td>이체 상태 조회</td>
<td>이의 제기 접수</td>
</tr>
<tr>
<td>이자 조회</td>
<td>카드 정지 해제</td>
</tr>
<tr>
<td>카드 분실 정지</td>
<td></td>
</tr>
</tbody></table>
<ul>
<li>카드 분실 정지는 위험을 줄이는 처리라서 챗봇이 바로 한다</li>
<li>정지 해제는 같은 카드에 대한 처리지만 위험을 늘리는 처리라서 상담원에게 넘긴다</li>
<li>1회차에서 정한 원칙과 같다: 위험을 줄이는 요청은 빠르게, 늘리는 요청은 신중하게</li>
</ul>

<h2 id="8-정리">8. 정리</h2>
<p><strong>정한 것</strong></p>
<ul>
<li>모든 상담 단계는 상담 이벤트로 남기고, 이관 패키지는 이벤트를 묶어서 만든다</li>
<li>이관 패키지의 필수, 선택, 담지 않는 항목</li>
<li>이관 기준 네 가지, 모두 규칙으로 판단</li>
<li>인증 승계는 시간과 처리 위험도로 판단</li>
<li>배정은 상담원이 가져가는 방식, 조건부 UPDATE로 한 명만 성공</li>
<li>챗봇은 조회와 위험을 줄이는 처리까지</li>
</ul>
<p><strong>가정으로 남긴 것</strong></p>
<ul>
<li>해석 실패 2회, 인증 유효시간 10분, 이탈 후 재접속 30분, 상담원 무응답 60초</li>
<li>모두 정책 데이터로 분리해서 바꿀 수 있게 한다</li>
</ul>
<p><strong>다음에 정할 것</strong></p>
<ul>
<li>가상 은행의 카드 승인 내역에 어떤 상태를 둘지 (승인, 매입, 취소)</li>
<li>응답을 받지 못한 결제 승인을 실제 결제 시스템에서는 어떻게 정리하는지 (금테크에서 추가 조사)</li>
<li>상담 이벤트와 이관 패키지의 데이터 구조</li>
</ul>
